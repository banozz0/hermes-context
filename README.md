# Hermes Context

Live Hermes Discord sessions in your menu bar.

A macOS menu-bar app for [Hermes Agent](https://github.com/NousResearch/hermes-agent). It lists every Discord session your Hermes profiles are running, shows how full each one's context window is and whether it is working, waiting on you or idle, and keeps a private local history of context usage. It never stores a message.

## Install

```sh
curl -fsSL https://github.com/banozz0/hermes-context/releases/latest/download/install.sh | sh
```

You need:

- macOS 14 or later, on Apple silicon or Intel.
- Hermes Agent 0.21.5 or later, with the `hermes` command on your PATH.
- A Hermes Discord gateway. Only Discord sessions are shown.

The installer stops before changing anything when macOS is older than 14, or when Hermes is missing or older than 0.21.5 (a `hermes --version` it cannot read does not stop it). It downloads the app into `/Applications` (else `~/Applications`), runs `hermes -p <profile> plugins install banozz0/hermes-context/hermes_context_observer --ref <commit> --enable --force` for every profile `hermes profile list` shows, default included, and opens the app. `plugins install --enable` asks a running gateway to reload its plugins over its control socket, so no restart is needed; when no gateway answers, the installer names those profiles and says to run `hermes gateway restart`. Because curl sets no quarantine flag, Gatekeeper never blocks the ad-hoc signed app. The app and the plugin always come from the one commit the release stamped into the script.

Run the same line again to connect a profile added later or to update. A profile already running this release's observer and an identical app are left alone.

To uninstall:

```sh
curl -fsSL https://github.com/banozz0/hermes-context/releases/latest/download/install.sh | sh -s -- --uninstall [--purge]
```

Uninstall removes the plugin from every profile and deletes the app. History (`~/Library/Application Support/dev.banozz0.hermes-context`) and each profile's bridge files stay unless `--purge` is given.

## What you see

- The menu-bar item counts the sessions working right now and turns into a warning triangle when any session's context reaches your threshold (30% by default).
- One flat list: sessions that need you, then working ones, then the rest by latest activity. Each row shows the Discord thread name, profile, state and context percent. **Live Status** adds channel, model and idle time; **Minimal** is one line per session.
- Search by session name, profile, model or `#channel`.
- Click a row for its details: context in tokens, model, current tool, timing, and an **Open Discord** button that jumps to the thread.
- A session idle for 24 hours (1–168, in Settings) leaves the list and comes back as the same row on its next message.
- When a gateway stops, its sessions stay on screen marked **Offline**.
- When a Hermes update switches off part of the plugin, a note names what is missing and says to rerun the install line.
- **Insights** (⌘I) shows mean, median and peak context use per session, per profile and overall, exports your history as CSV or JSON, and clears it.

## Privacy

Everything stays on your Mac. The plugin writes only the metadata fields its JSON schemas allow: profile, Discord location, session name, state, model, context size and, per tool call, the tool's name, skill name, estimated result size, duration and status. Prompts, responses, tool arguments, tool results and error text never reach any file. The app reads those files and four fields of Hermes's own gateway status files (`pid`, `gateway_state`, `served_profiles` and `start_time`), never writes Hermes state, sends no prompts, opens no network port and posts no notifications.

## How it works

An observer plugin in each Hermes profile writes an atomic snapshot of that profile's live Discord sessions, plus one small event file per model request and tool call, under `<profile-home>/hermes-context/v1/`. The app watches those files, shows the snapshots and imports the events into a local SQLite history. The rest of this README is the full contract and the app's exact behavior.

## Contract

Each participating Hermes profile writes `<profile-home>/hermes-context/v1/snapshot.json`. The schema is `contracts/v1/snapshot.schema.json`; the strict Python validator is `hermes_context_observer.contract.validate_snapshot`. Unknown fields are rejected at every level. Writers take an advisory lock on the stable, mode-0600 `snapshot.lock`, reconcile the latest validated rows, write a complete document to a mode-0600 temporary file, and atomically replace the destination. The directory is mode 0700. Readers should parse/validate the complete replacement; never use temporary or lock files.

`routing_id` is a stable SHA-256 identity of `[profile, platform, chat_id, thread_id-or-empty]` prefixed `hc1:`. The input is compact JSON with UTF-8 encoding and no ASCII escaping. It is not a session generation ID. `/new` and resets replace the lane's current `session_id`, set `previous_session_id`, preserve `lineage_root_id`, and clear turn-scoped measurements. A separate profile in the same Discord thread has a separate snapshot and routing ID. Snapshots hold only current generations; historical generations are linked through events.

Each completed top-level Discord `post_api_request` with a Hermes `api_request_id` publishes exactly one immutable JSON event (`kind: model_request`) under `<profile-home>/hermes-context/v1/events/<segment>/<sequence>-<event_id>.json`, and each completed top-level Discord `post_tool_call` with a `tool_call_id` publishes exactly one `kind: tool_call` event in the same tree and sequence. Tool calls are admitted by the same rules as requests. Delegated child calls are excluded: children inherit the parent's route but own different session IDs, so their hook callbacks cannot write to the parent's live lane or its history. A `/new` hook explicitly rotates the lane. Without a reset hook, the observer admits either a canonical `SessionDB.get_compression_chain` successor or the session ID currently owned by the same key in the gateway's process-home routing index; an unrelated borrowed route cannot take over. This covers silent recovery and `/resume` without inventing a new identity for a resumed generation. An ended generation keeps its original lineage and predecessor, while a never-before-seen generation inherits the lane's root and current predecessor. Under the same profile lock, each transition saves the ended generation's six allowlisted identity/lineage/model fields in an append-only, hashed-key `generations/` record before publishing the replacement snapshot. This makes a late completed request attributable even when an intermediate generation emitted no earlier event; unknown IDs and competing compression siblings cannot invent lane generations. Generation records never contain conversation or tool content and are retained alongside event segments; rotation never prunes them. `contracts/v1/event.schema.json` and `validate_event` strictly allowlist both record kinds; `kind` is required and picks the field set. A request's event ID is `hc1:` plus SHA-256 of compact UTF-8 JSON `[profile, session_id, api_request_id]`; a tool call's is the same hash of `["tool_call", profile, session_id, api_request_id, tool_call_id]` (an absent request ID is `""`). Hermes makes tool-call IDs unique only within one model response, so the issuing request keeps a reused ID from swallowing a later call, and the `"tool_call"` tag keeps it apart from every request identity. Raw request and tool-call IDs are never written. The positive `sequence` is per-profile and monotonic, usable for cursor and gap detection. The observer allocates it under the snapshot lock from the newest segment alone, writes a mode-0600 temporary file, fsyncs it, publishes by exclusive link, and fsyncs the containing directory (and `events/` for a segment's first event). Each append first hard-links the newest published event as `event-ids/<event_id>.json`, beside `events/`, so a replay of the same request or tool call finds the existing record with one lookup and does not write another; the index trails the tree by that one event, so a crash mid-append never leaves it behind, and an append never lists the whole tree. Segments rotate after 1,000 events (configurable only for fixtures); old segments are never rewritten, truncated, or removed, so an importer can catch up after downtime. Retention is owned by the app, not by rotation. Request events retain only profile, routing/lineage/generation IDs, timestamp, model/provider, state and context occupancy (`used`, `maximum`, `percentage`, `source`, `measured_at`); a request with unknown occupancy still gets an event with null context fields. Tool-call events retain only profile, routing/lineage/generation IDs, `request_event_id` (the issuing request's event ID, null when Hermes named none), completion timestamp, `tool_name`, `skill_name`, `estimated_tokens`, `duration_ms` and `status`. `estimated_tokens` is Hermes's `estimate_tokens_rough` of the result the hook receives (a multimodal result goes through `estimate_messages_tokens_rough`, which prices images); the result itself goes no further than that call. `status` is `ok`, else `error` (Hermes's `blocked`, `cancelled` and `timeout` included); the error message is never read. `skill_name` is set only for a successful `skill_view`, from its `name` argument, the one argument the plugin reads: a failed call's name is whatever the model typed. Current tool and any conversation contents, tool arguments, results or error text never enter event files. Importers should enumerate segment directories in order, validate every record, dedupe by `event_id`, and detect skipped sequence numbers per profile.

`state` is `working`, `needs_attention`, or `idle`. `current_tool` is a transient name, never arguments or results. `context.used` is provider-reported prompt occupancy, not accumulated lifetime tokens; without a provider measurement occupancy stays null, and without a known context window `used` stays while `maximum` and `percentage` are null. `discord_route.channel_label` is the lane's Discord channel (a thread's parent) as `#name`, read from the profile's own gateway `channel_directory.json`, flattened to one line and capped at 100 characters; it is null when the directory does not know the channel. Hermes hands threads a combined `Guild / #channel / thread` name, and the plugin removes that prefix only when the directory supplies the exact guild and channel names. Thread names take precedence for display; unthreaded sessions use the generated title from that profile's read-only Hermes state store when available, else a non-ID fallback. The plugin never copies hook request/response objects into the observer.

The plugin imports and calls Hermes only through `hermes_context_observer/compat.py`, whose `INTERNAL_FEATURES` and `HOOK_FEATURES` map every Hermes function, class and hook the plugin uses to the features a Hermes without it switches off. The optional top-level `degraded` names what the running Hermes switched off: a sorted, non-empty array of unique names from the closed set `sessions`, `titles`, `context_window`, `lineage`, `backfill`, `tool_history`, `attention`, `startup` and `subagents`. Absent means nothing is lost. A feature is lost when a Hermes internal it needs raises `ImportError`, `AttributeError` or `TypeError`, or when Hermes's list of valid hooks, checked at registration, lacks a hook it registers (a Hermes without that list skips the check). The plugin then logs one warning to Hermes's log, falls back and keeps running, and no error text reaches the snapshot. `register` and every hook callback catch every exception and log the first one per callback, so a Hermes change can cost features but never the plugin's load or a Hermes turn. The fallbacks:

- Home resolution: without Hermes's home lookups the profile and routing homes become `HERMES_HOME`, else `~/.hermes`. That is Hermes's own process-home rule, so a multiplexed gateway's lanes still list. The guess is unconfirmed, so a lost profile-home lookup reports `sessions` and a lost routing-home lookup reports `lineage` and `backfill`.
- `sessions`: without the session accessor the plugin still beats and reports it from its first snapshot.
- `titles`: an unthreaded row keeps its non-ID fallback name.
- `context_window`: `context.used` stays, with `maximum` and `percentage` null.
- `lineage`: without the compression chain only the routing index's owner is admitted; without the routing index, the task's own session.
- `backfill`: otherwise no lanes are listed at activation.
- `tool_history`: no tool-call event is written, and the lane still updates.
- `startup`: without the runtime-lock check the observer activates at the first gateway dispatch.
- `subagents`: a child's requests are left to lane admission, which refuses a session the routing index does not give the lane.

Like the heartbeat, `degraded` is the gateway owner's report; another process's write keeps it, and the next gateway that loses nothing drops it.

On activation the gateway owner first backfills: it reads Hermes's gateway routing index read-only and adds an idle row for every Discord lane of this profile that the snapshot lacks, so an install lists current sessions before their next request. A lane is this profile's when its session is in the profile's own state database (a multiplexed gateway keeps every profile's lanes in one index); finalized entries are skipped and rows already held win. A backfilled row's context is the entry's `last_prompt_tokens` (the provider-reported prompt size of the lane's last request; zero means no request yet, so occupancy stays null), `source` `provider_reported`, measured at the entry's update time converted from Hermes's naive local time to UTC. Backfill writes no event, because no request ran. The gateway publishes a complete snapshot synchronously when its plugin activates (even with zero sessions), then refreshes its profile-scoped heartbeat every 15 seconds without requiring inbound traffic. Activation needs Hermes's runtime lock. A served profile's plugins load after the gateway claims it, but the launch profile's load during gateway config loading, before the claim: that observer checks for the lock every second and activates (stale-row recovery, backfill, snapshot) once its gateway holds it. CLI plugin discovery never owns that lock and cannot start or refresh the heartbeat. Multiple plugin-loading processes in the same profile home can update session rows, but the lock and reload prevent an older in-memory lane map from erasing newer work; a CLI row update preserves the last gateway heartbeat. **Readers must derive offline status from `gateway.heartbeat_at` and `gateway.offline_after_seconds` using their own wall clock:** if the heartbeat age exceeds the timeout, preserve the last document and display it as Offline. On activation, a fresh shared snapshot keeps its in-flight rows; a stale snapshot restores rows as idle. Invalid or mismatched saved documents fail closed instead of overwriting unknown data.

### Tool usage the observer cannot see

- **Skills that skip `skill_view`.** `skills.auto_load`, `/skill` slash commands (stacked ones too), webhook, cron and CLI preloads put a skill in the prompt without a tool call. Hermes reports them only through `on_skill_lifecycle`, with an empty `session_id` (a gateway slash command fires it before the turn's session is bound), so no lane or generation can own them; the gateway's per-channel auto-skill fires no hook at all. Their text still counts in the next request's context occupancy, unattributed.
- **Size is the hook's result.** Hermes can still reshape a result after `post_tool_call`: past its persistence threshold (100,000 characters by default) it spills to a file and keeps a preview, and guardrail stubs, wrapping and the per-turn budget apply after the hook. A spilled result is therefore recorded at full size. On the sequential path the hook sees `transform_tool_result`'s output, on the concurrent path the raw result.
- **One record per (request, tool call ID), first hook wins.** Hermes's concurrent connector batch fires the hook for each sub-call under the parent's ID and again for the batch, so that call is recorded under its first sub-call's name and size. A timed-out call is recorded as its `timeout` (an `error`); a worker still running after the next model request started would record a second row under that newer request.

## Verification without live gateways

- `uv run --no-project --with pytest --python ~/.hermes/hermes-agent/venv/bin/python python -m pytest -p no:cacheprovider` checks tool-call records (shared sequence, request link, identity across replay and restart, admission, the allowlist, the JSON schema agreeing with `validate_event`, and a privacy sentinel in arguments, results and error messages through the registered hook), atomic replacement under concurrent reads, same-home two-observer and cross-process reconciliation, strict privacy allowlisting, fixed replay fixtures, event identity/segment rotation/replay, profile/thread isolation, reset lineage, gateway-down/CLI-alive Offline, no-traffic activation, restart recovery, install-time backfill from the routing index (names, context, skipped lanes, no events, and a later live request landing on the same row), a stale snapshot's idle reset surviving a transaction that writes nothing, a Hermes without its title lookup (one warning, and the row keeps its fallback name), a Hermes without each internal and hook in compat's map in turn (the plugin still registers and beats; `degraded` is exactly that entry's features; unless `sessions` is lost a completed request still measures context, its percentage unknown only without `context_window`; a subagent's request never lands on its parent's lane; without the lock check nothing beats before a gateway dispatches), served profiles keeping their lanes without Hermes's process-home lookup, the map listing every Hermes name compat imports and every `SessionDB` method it calls, an unforeseen error in a hook and a changed `register_hook` (neither reaches Hermes; one warning each), `degraded` kept across another process's write and dropped by a gateway that lost nothing, and the snapshot schema agreeing with `validate_snapshot` on `degraded`'s closed names, uniqueness and non-empty list (JSON Schema cannot require sorted order; `validate_snapshot` does). The no-project mode avoids creating a local virtualenv or lockfile; the Hermes interpreter supplies upstream dependencies.
- `~/.hermes/hermes-agent/venv/bin/python tests/probe_plugin_discovery.py` loads the plugin through Hermes's actual plugin manager in disposable A→B→A profile homes, holds/releases Hermes's real runtime lock to emulate gateway ownership, checks same-home two-manager no-loss, CLI-alive gateway-down Offline, immediate no-traffic startup snapshots, a no-traffic restart from a stale saved snapshot, and a third profile whose already-routed lane is backfilled at discovery, fires lifecycle, request and tool-call hooks with task-local Discord routing, verifies profile-isolated files with no argument, result or error text in any bridge file, and removes the homes. `HERMES_CONTEXT_PROBE_KEEP=<dir>` first copies both profiles' bridge trees to `<dir>/profiles/<name>/hermes-context`, a root the headless app can import. Both find Hermes's source checkout through the Python running them; `HERMES_AGENT_SOURCE` points them at another. Do not copy the plugin into the real profile or restart the gateway during this phase.

The fixed snapshots are `fixtures/v1/alpha.snapshot.json`, `fixtures/v1/beta.snapshot.json`, `fixtures/v1/before-reset/alpha.snapshot.json` (alpha before `/new` rotates thread-1) and `fixtures/v1/list/gamma.snapshot.json` (needs attention, measured context, a current tool, an unthreaded lane idle for over a day). `fixtures/v1/events/replay.json` has deterministic alpha→beta→alpha completed requests and tool calls with a reset, including one unknown occupancy, a failed call, two `skill_view` calls and a late call from the generation the reset ended. The replay tests generate snapshots and events through the real `Observer` and fail on drift. They are deterministic public fixtures, not captured transcripts. The plugin discovery probe invokes real Hermes hooks in A→B→A order without contacting Discord or an LLM.

## Native app (`app/`)

A SwiftPM package: `HermesContextCore` (decoder, profile discovery, FSEvents watcher, list model) and the `HermesContext` SwiftUI `MenuBarExtra` app. No Dock icon, no network port.

- Discovery reads `~/.hermes/hermes-context/v1/snapshot.json` and `~/.hermes/profiles/<name>/hermes-context/v1/snapshot.json`; a profile without the plugin is simply absent. `HERMES_CONTEXT_HERMES_ROOT` overrides `~/.hermes`.
- One row per `routing_id`, so `/new` updates its lane in place and two profiles in one thread stay two rows. Order: Needs attention, Working, Idle, then latest activity. Hermes never closes a Discord session on its own, so an Idle lane whose last activity is at least N hours old (default 24, 1–168 in Settings) counts as closed: it is hidden from the list, search, the working count and the warning, and comes back as the same row when its last activity moves forward. Stalled Working or Needs attention lanes never hide. Insights still names a hidden lane from its row.
- Search (always shown) matches every whitespace-separated term, case- and accent-insensitive, against session name, profile, model and Discord channel label (`#ops`). Session and Discord IDs are never searched.
- A row opens its details in place: profile, state, context (percent, tokens, estimate flag, measurement age; when Hermes can't say the window size, tokens show alone, as `90k tokens`, and the row's percent stays `—`), model and provider, current tool (Working only), turn start, last activity and Discord location, with session, previous session, lineage root and routing ID under a collapsed Diagnostics group. Nothing else reaches the pane: the decoder maps only contract fields.
- Open Discord targets `https://discord.com/channels/<guild>/<thread, else channel>` (`@me` without a guild), through the Discord app as `discord://-/…` when one claims that scheme. IDs outside `[A-Za-z0-9_-]` or a non-Discord platform get no link.
- A profile is Offline once `now − gateway.heartbeat_at > offline_after_seconds` on this Mac's clock (or the writer declared `freshness: offline`). Its rows stay, marked Offline with their last known state; an empty but fresh snapshot is simply online with no rows. A 15-second tick catches a gateway that stopped writing.
- Two views, switched in the popover footer or Settings and remembered across relaunch: **Live Status** (the detailed row: name, profile, state, channel, model, context percent, idle time) and **Minimal** (one line: name, profile, state, context percent).
- The menu-bar item shows the number of Working lanes whose gateway is live (an Offline lane's Working is only its last known state) and swaps its icon for a warning triangle while any visible lane's latest occupancy is at or above the context threshold (default 30%, 1–100). The popover lists those lanes under "Context at or above N%". Search never changes either. There is no notification path: no UserNotifications framework, API or permission.
- First run (the popover until answered) says the app keeps only metadata and asks whether to launch at login; the answer is recorded and applied through `SMAppService.mainApp`. Settings (gear in the footer) hold the view, the threshold, the idle hide age, launch at login, a way to Insights for history export and clear, and the bridge diagnostics with the root being read. Settings live in the app's own defaults domain, `dev.banozz0.hermes-context`.
- A live profile whose snapshot has `degraded` gets one diagnostic line naming the lost features, then "Rerun the install line for the latest Hermes Context." The words are: `titles` session titles, `context_window` context window sizes, `lineage` session history links, `backfill` sessions listed at startup, `tool_history` tool history, `attention` needs-attention status, `startup` status at gateway start and `subagents` subagent filtering, as in "A Hermes update switched off session titles and tool history." With `sessions` lost the line reads "Hermes Context can't see its sessions." instead, since nothing else shows. An Offline profile shows only its offline line. The decoder rejects a name outside the closed set, or a repeated one, like any other malformed snapshot.
- A profile Hermes runs whose plugin stays silent shows "Hermes runs <profile>, but Hermes Context gets nothing from it. Rerun the install line." in place of its offline line, once its gateway has run for at least 60 seconds while its snapshot is missing or Offline. Hermes runs a profile, by its own rule, when the profile's `gateway_state.json` names a live gateway, or the root `~/.hermes/gateway_state.json` does and lists the profile in `served_profiles`. A file names a live gateway when its `gateway_state` is `running` (or `degraded`, some platforms parked) and its `pid` is a live process, any user's, whose creation time matches `start_time` (centiseconds since the epoch on macOS). That is Hermes's own guard against a recycled pid; the app allows the 2 seconds of drift Hermes's reconciliation allows, and checks it in the kernel's process table without signalling anything. From those files the app reads, read-only, only `pid`, `gateway_state`, `served_profiles` and `start_time`. A status file that is missing, unreadable or reshaped, or has no `start_time`, adds no line: the profile shows its offline line as before, or nothing when it has no snapshot. A snapshot that fails to read keeps its read-failure line alone. The next read after the plugin beats again drops the line, and the 15-second tick picks up a gateway starting or stopping.
- A file that fails to read or decode (corrupt, unsupported contract, unreadable) never blanks the other profiles. It shows as a diagnostic above the footer, and if that file decoded earlier in this run, its last good snapshot stays on screen, still aging to Offline by its own heartbeat. A snapshot file that disappears takes its profile with it.

### Telemetry store

At launch, on every bridge change and on the 15-second tick, the app imports, off the main thread (a burst queues one import), each profile's new event files (`<home>/hermes-context/v1/events/`) into SQLite at `~/Library/Application Support/dev.banozz0.hermes-context/telemetry.sqlite`. The store creates the directory 0700 and the database 0600 before SQLite opens it, and SQLite gives its WAL and shared-memory files the same mode. An existing directory keeps its mode. `HERMES_CONTEXT_DATABASE` overrides the path. A run that overrides `HERMES_CONTEXT_HERMES_ROOT`, or runs headless, without it keeps no history, so a fixture root can never write the real one.

- **Decoder.** `EventDecoder` is the strict v1 event contract. An unknown field anywhere rejects the record. The event's profile must match its home (`default` for the root, else `profiles/<name>`), and the sequence and event ID in the file must match its name. A home Hermes names `custom` (a symlinked profile directory) therefore has its events rejected, and that shows as an issue. Temporary files and the observer's `generations/` and `event-ids/` records are never read.
- **Decoder kinds.** `EventDecoder` returns a `TelemetryRecord`: `.request` or `.toolCall`, chosen by the record's `kind` before its fields are checked.
- **Exactly once.** `event_id` is the primary key of each table. A per-profile cursor (sequence, event ID, segment) commits in the same transaction as each batch of 500 events, so a crash rolls back only the open batch and a relaunch resumes at the cursor. Files are read in (sequence, event ID) order, so two files that share a sequence number are both stored. If the cursor's file is gone, the event tree was rebuilt: the importer records `history_reset`, reads the whole tree again and drops known event IDs. Event files are never pruned; the next sequence comes from the highest file on disk.
- **Issues.** A missing sequence (`gap`), another contract version (`unsupported`), a record outside the contract (`malformed`) or an unreadable file becomes one `ingest_issues` row, is never retried (an unreadable file included), and never blocks the events after it. Reasons name fields, never values, so a rejected record's contents never reach the database. Each profile with skipped records gets one diagnostic line in the popover and Settings ("History skipped N event records: missing, corrupt or unsupported."); a gap counts every sequence number it spans.
- **Schema** (`user_version` 2; a newer one is refused). Migrations run in order, one transaction each: 1 created the request tables, 2 adds `tool_calls` and leaves observations, cursors and issues untouched. `observations` holds only the approved request fields (profile, sequence, routing, lineage root, previous and current session, timestamp, model, provider, state, and context used, maximum, percentage, source and measured-at time) in STRICT columns. `tool_calls` holds only profile, sequence, routing, lineage root, previous and current session, `request_event_id`, timestamp, tool name, skill name, estimated tokens, duration and status. There is no column for a current tool, arguments, results or error text, and none can hold a serialized payload. Timestamps are UTC text with milliseconds. `import_cursors` and `ingest_issues` hold import state only.
- **Tool usage.** `toolCalls()` returns every call oldest first. `requestEventID` is its request observation's `event_id` and `(routingID, sessionID)` its generation, so an agent can rank tools and skills by `estimated_tokens` per request, generation, lane or profile.
- **Lineage.** A generation is `(routing_id, session_id)`, its own statistical unit. `lineages()` groups generations under their routing lane, newest lane first, taking each generation's root and predecessor from its first request. A cross-thread `/resume` puts one session ID in two lanes as two generations.

### Insights

The chart button in the popover footer (⌘I), or Settings › History, opens Insights: a separate, resizable window, built on first open and reused, never shown at launch.

- **Statistics** (`InsightsReport`, from `TelemetryStore.insights()`): count, arithmetic mean, median and peak of `context_percentage` per session generation, per profile and overall. Every model request weighs the same; nothing is time-weighted. A request with unknown occupancy counts under Requests but not under Measured, and mean, median and peak are over the measured ones. The median of an even count is the mean of the two middle values. Tables round to at most one decimal; the report holds the exact values.
- **Navigation.** Generations are grouped under their routing lane, most recent lane first. A lane is named after its live row when the bridge still lists it, else after when history first saw it: history keeps no names. A generation is Current when the live row runs it, Ended when a later generation replaced it, and Latest when its lane is no longer live.
- **History unavailable.** A database that fails to open, or an import or clear that fails, replaces the tables with "History unavailable" and the reason; the live list is unaffected. A failed import or clear is retried on the next bridge change or tick, and its success restores the tables, rebuilt from the database because the failure may have committed part of its work. A database that failed to open stays unavailable until the app relaunches. A run that keeps no history says so.
- **Export** (`HistoryExport`): Export CSV… and Export JSON… save every stored request and tool call through a save panel, under the database's field names and nothing else. Timestamps are UTC ISO 8601 with milliseconds (`2026-09-24T10:00:30.000Z`). JSON is `{"format": "hermes-context.history.v1", "exported_at", "timestamps", "fields", "requests", "tool_calls"}`, where `fields` names and explains every field and a record keeps its null fields. CSV is RFC 4180 (CRLF lines; a cell with a comma, quote or line break is quoted, quotes doubled) with a `kind` column (`model_request` or `tool_call`) first, then every request field, then the tool-call fields; a field a row's kind lacks, and a null, is an empty cell. Rows run in event order.
  - Both kinds: `event_id`, `profile`, `sequence`, `routing_id`, `lineage_root_id`, `previous_session_id`, `session_id`, `timestamp` (completion, UTC).
  - Requests: `model`, `provider`, `state`, `context_used`, `context_maximum`, `context_percentage` (0 to 100), `context_source`, `context_measured_at`.
  - Tool calls: `request_event_id`, `tool_name`, `skill_name` (successful `skill_view` only), `estimated_tokens` (Hermes's rough estimate), `duration_ms`, `status` (`ok` or `error`).
- **Clear.** Clear History… asks first, inline, naming how many requests and tool calls it deletes, plus anything published since; only Clear All History deletes. It imports anything pending, deletes every observation, tool call and skipped-record issue in one transaction (so the "History skipped" diagnostic resets with the history it described), then runs `VACUUM` and a truncating WAL checkpoint so no deleted row survives in the database, its WAL or its free pages. A checkpoint another connection blocks fails the clear visibly instead of leaving deleted pages in the WAL unreported. The import cursors stay: event files are never pruned, so without them the next import would read the whole history back. Events published after the clear import as usual. Nothing outside the database is written: snapshots, event files and Hermes's own sessions and transcripts are untouched.
